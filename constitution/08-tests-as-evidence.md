# 8. Tests as Evidence

This chapter answers two questions about a diff: what evidence arrives with the change, and what the difficulty of producing that evidence reports about the production design. It governs which claims a passing test can close, what a test may fake, and how test code and test edits are reviewed — not the one-hat rule for restructuring, which belongs to chapter 9.

### 8.1 Require a test that fails without the change, and a bug fix to carry the smallest reproducing case
**Finding:** For every behavioral change in the diff, name the test that would go red if the change were reverted. If none exists, that is the finding, and it names the specific missing case rather than asking for tests in general. A change presented as a bug fix owes the smallest test that reproduces the defect at the level the fault lives — an end-to-end scenario as the only evidence for a localized logic error leaves the hole open. "Verified manually", "the nightly suite covers it", and a bespoke rig outside CI are not evidence: the artifact must be one the shared build runs.
**Unless:** Pure restructuring changes no behavior and owes no new test — it owes the tests that already existed and passed. No test is owed for debug aids, trivial accessors, generated pass-throughs, or a thin adapter that only forwards to an un-automatable edge without branching. Rigor scales with consequence and expected lifespan: a spike or a quarantined experiment is not held to the bar a payment path is. And a green test is necessary but never closing for a universal claim — never deadlocks, always authorized, this invariant holds — which needs locatable enforcement instead; performance and capacity claims need a measurement on the running system.
**Sources:** (02, 06, 08, 09, 24) F15, F2

### 8.2 Assert observable results through the public protocol, never the internal steps taken
**Finding:** New or changed assertions that read private state, cast to a concrete type, count or order calls to in-process collaborators, pin an intermediate value, or match the exact text of a generated artifact whose effect is what matters. These go red on refactorings that alter nothing observable, and the false alarms are what eventually gets the suite ignored or disabled. Assertions that merely rule out nothing — not null, not zero, no exception thrown — are the same finding from the other side: they pass for almost every wrong answer.
**Unless:** An interaction that genuinely leaves the system is an observable result and a legitimate assertion target, as is order or count where the protocol is the contract — a message sent exactly once, a step that must follow its trigger. Values with no single right answer (timestamps, generated ids, floating point) are asserted by property or tolerance. A test that pins internals to lever one design step forward is scaffolding: acceptable only while the behavior is also covered from outside, and expected to die. Legacy code being pinned before restructuring is not the place to enforce this.
**Sources:** (05, 08, 09, 11, 24, 25, 26) F6

### 8.3 Refuse production surface whose only reason to exist is a test
**Finding:** A private member turned public, protected or virtual; a test-only accessor, setter or subclass hook; a branch or constructor parameter keyed on test or staging environment; an interface, factory or wrapper introduced over an in-process collaborator with the word testability as its justification. Indirection pays rent by an existing consumer or a genuinely one-way boundary, and a test counts as that consumer only when it actually substitutes across the seam for something the outside world observes. A private routine too complex to reach through the public API is a missing class, not a visibility problem.
**Unless:** A member that is genuinely part of a contract with an outside consumer — persistence hydration, a serializer — is observable behavior, not a backdoor. The legacy exception is real and narrow: where the touched code is pre-existing, untested, and this diff is actively bringing it under test, a declared in-source seam (widened visibility, extracted interface, injected collaborator) is accepted as booked debt with a named follow-up. Reflection or covert access into privates stays blocked in every case, and so does an undeclared seam in code that is new or already under test.
**Sources:** (06, 07, 08, 09, 24, 25, 26) F1, F11

### 8.4 Double only what the outside world can observe, and put the feature's evidence at the right level
**Finding:** A double standing in for an in-process collaborator, a database the application alone owns, or a third-party type the team does not own — replace it with the real thing and assert final state, or with a thin owned adapter that is integration-tested. Place a justified double at the outermost adapter, not several layers in. On level: a user-visible feature with no single outside-in test through the real entry point in the system's own vocabulary is missing evidence, and the symmetric finding fires too — slow, infrastructure-backed tests re-covering variations and error cases that a fast in-memory test would cover exactly as well.
**Unless:** A double is justified where the dependency is out-of-process and its call pattern is observable outside the system, where the real thing is slow, nondeterministic or side-effecting, or to provoke a failure that is hard to produce for real. A store shared with other applications behaves as externally observable and warrants the double. Refactorings and internal cleanups need no outside-in test; a thin CRUD change may legitimately carry roughly equal numbers at both levels. Where a real dependency cannot run in the environment at all, skipping the wider test beats faking it.
**Sources:** (08, 24, 25, 26) F6

### 8.5 Read an awkward test as a report on the production code, and fix the production code
**Finding:** Test setup disproportionate to the behavior asserted, a wall of expectations, a chain of stubs built just to construct the subject, a test that breaks for reasons unrelated to what it asserts, or a test forced to reproduce ambient state — a static clock, a global cache, an environment or config read, a singleton, a collaborator the unit constructs for itself. The unit under test both deciding and performing I/O is the same finding in its most common form: ask for a collaborator-free decision plus a thin performer that carries it out. The remedy lands in production code; loosening the test hides the signal.
**Unless:** Persistence, concurrency, asynchrony and UI are intrinsically awkward, and friction from the platform is not evidence against the design — test difficulty opens an investigation, it is not by itself a verdict. Adapters and the composition root exist to touch ambient state; the rule targets the deciding layer. Full purity has its own cost, so do not demand the split in trivial or low-stakes code, and one or two in-process collaborators do not make a class wide. Pre-existing ambient state the diff merely lives beside is not automatically in scope.
**Sources:** (06, 07, 08, 09, 24, 25, 26) F6

### 8.6 Sabotage the green suite before accepting it
**Finding:** Mentally replace the changed implementation with a hard-coded constant or a degenerate version and ask whether the new tests object. If they would still pass, the change is unevidenced whatever the suite says. Three concrete forms this takes in a diff: an expected value computed from the inputs by the same rule the code under test uses — a mirror of production that cannot distinguish a regression from a refactoring, so require a literal from an independent source; one constant reused for two roles, which cannot catch swapped arguments; and a new comparison, loop bound or index with no case at its boundary. Coverage percentage is not an answer to this question — it counts lines executed, not outcomes verified.
**Unless:** Do not demand combinatorial boundary coverage — one representative per equivalence class away from the boundary the diff introduces. Some values genuinely have no independent source, and for trivial operations the mirror objection barely bites. A sharp coverage drop in core logic is real evidence of a gap even though a high number proves little.
**Sources:** (02, 08, 09, 26) F6, F15

### 8.7 Review test code at production rigor: one named behavior, no logic, a failure that locates the fault
**Finding:** A test asserting several unrelated behaviors, or named so that its failure does not say what broke. Logic inside a test body — a branch, a loop, string concatenation, a computed expectation — because tests have no tests of their own and must be correct on inspection. Values that are not obviously canned, so the reader cannot tell which one the assertion depends on. A sleep used as synchronization, a test that depends on another having run first, shared mutable fixture state, or an acquired resource with no release: an order-dependent suite is a suite that lies, and flakiness destroys the value of every test beside it.
**Unless:** Repetition in tests is not a smell — explicit duplication that keeps each case readable beats a shared helper that makes failures undiagnosable. Data builders with overridable defaults and separately tested test infrastructure are fine. Two obvious arguments need no builder. Shared fixtures are a legitimate trade where fresh state is genuinely too slow, but the usual fix is cheaper setup rather than shared setup.
**Sources:** (02, 08, 09, 11, 24, 25) F6

### 8.8 Scrutinize test edits harder than production edits
**Finding:** A deleted test, a removed case, or a weakened assertion in the same diff as a production change is an automatic block — that is the safety net being cut by the change it was there to catch. Pruning on its own is allowed with the burden on the deleter: name which other test fails if this one goes, demonstrated from current logic rather than from surface similarity. A test deleted, skipped or commented out to make the suite green is never accepted. Prefer additive test edits, and keep a test-only refactoring in a diff with no production changes.
**Unless:** A tooling-applied atomic rename across both sides is fine, and a signature change that mechanically breaks compilation in tests is not a weakened assertion. Moving a slow test to a later stage is not deletion. A test protecting a distinction that no longer exists is inertia and may go — but keep a suspicious duplicate whenever removing it would cost any confidence. On characterization tests over legacy behavior, silence is the finding in both directions: a quirk pinned with no callout, and worse, a quirk silently corrected inside a diff that claims to preserve behavior.
**Sources:** (05, 06, 09, 11, 24) F6, F11
