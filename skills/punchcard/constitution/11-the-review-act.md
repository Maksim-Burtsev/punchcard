# 11. The Review Act Itself

This chapter answers how the reviewer spends attention and what closes a claim: where rigor rises and falls, what evidence a given kind of promise owes, how a finding must be written to be actionable, and what the reviewer does with history, with a bug fix, and with a shortcut they are willing to approve. It governs the conduct of the review, not the substantive rules the other chapters supply.

### 11.1 Set rigor by consequence, never by diff size
**Finding:** Before commenting, price the change: what does it cost if it is wrong, how exposed is the shape it establishes, how long will this code live, and how often is this region edited. Raise the bar where failure is expensive or the shape is hard to undo — a trust boundary, a concurrency or authorization path, a published or cross-team surface, a wire format, a schema, data crossing a boundary, or code that is hot or brand new. Lower it on precedented, low-stakes, cold code, where a net improvement is approved as an improvement rather than held against the ideal design. The finding fires in both directions: a one-line config flip, boolean default or constant edit reviewed casually because it is small — the size band where wrong changes actually cluster — and an equal-weight deep-design objection filed on a cold file nobody reads. The unit priced this way is the whole element the change lands in, not the code lines alone: tests, configuration, build and CI definitions, migrations, generated inputs and infrastructure declarations carry the same consequence and get the same reading.
**Unless:** Low churn is not proof of quality — quarantined and dead code look equally stable, and new code cannot yet be known to be cold. Proportionality never discounts a defect the reviewer can actually demonstrate: correctness, data-loss and security findings are priced by their consequence, which small diffs do not reduce. Deliberate experiments, spikes and code with a stated short lifespan are legitimately held to a lower bar, but only where that status is visible in the repository rather than asserted in the pull request.
**Sources:** (02, 08, 18, 19, 22, 32, 33) F2

### 11.2 Classify the claim before pricing the evidence that closes it
**Finding:** Name what the change promises, then demand the matching artifact. An existential claim — this input now yields that output, this bug no longer reproduces — is closed by a check that runs in the project's automated suite, and its absence is a blocking finding that names the specific missing case. A universal claim — this never deadlocks, this is always authorized, this invariant always holds, this protocol always conforms — takes tests as necessary but never as closing: demand enforcement the reviewer can point at, such as a type that makes the illegal state unrepresentable, a store constraint, a single-writer rule, or a static check covering every execution. A performance, capacity or compatibility claim — anything the diff asserts it made faster, cheaper or larger — is closed only by a measurement on the running system, naming the workload, the point the number was taken at, and the fraction of end-to-end time the touched code held; a model, an argument from first principles, a benchmark of the wrong shape or one that cannot reach the layer it names, a proxy metric standing in for latency (operations per second, utilization, hit ratio), and a mean over a bimodal system close nothing, and a tuning value owes a mechanism rather than a better number. That demand binds claims of improvement only: a cost the reviewer reads off the diff is licensed without a profile in the three shapes 11.9 sets out, and stays a note outside them (F16). Whatever the class, sabotage the green suite before accepting it: ask whether a hard-coded or degenerate implementation would still pass, and if it would, the evidence is decoration. A claim stated so that no observation could contradict it is itself the finding — ask for it restated as stimulus, response and measure, or as a cost with a named payer.
**Unless:** Demanding structural proof for an existential claim is overkill, and demanding a measurement for a low-stakes quantitative claim is ceremony — arithmetic on the back of an envelope is the right evidence for a cheap claim. Rationale is owed only where the change establishes a rule other code must follow: a new boundary, a communication style, a data-ownership shift, a lock-in dependency, or a quality claim the approval rests on. Design choices contained inside one module belong to the author, and asking what else they considered is a comment, not a finding.
**Sources:** (01, 02, 07, 08, 09, 18, 19, 27, 31, 32, 33) F15, F16

### 11.3 Make every finding concrete, located and labeled with its mode
**Finding:** A comment that blocks must name something specific and fixable, anchored at the line where the problem is, with the change that would resolve it. Vague disapproval, a preference stated as a defect, and an objection whose remedy is redesigning what the author chose are all noise that trains authors to skim reviews. State which mode each finding is in — blocking, or a note that does not gate the merge — because an unlabeled deep-design objection reads as a block and gets resented as one. Among defensible approaches, defer to the author: the reviewer's alternative being equally good is not a finding.
**Unless:** Reviewer confusion is a real defect and is always reported even when the concrete cause takes work to locate — but it is pinned to a cause before it blocks (see 2.2), never filed as an unlocated complaint. Deference to the author ends where the change is not merely different but demonstrably wrong, or where it establishes a rule other code must follow.
**Sources:** (02, 08, 09, 18, 23) F2, F15

### 11.4 Read the version history as evidence, not just the diff
**Finding:** Where history is available, it is admissible and often decisive. Repeated fixes landing in the same region say the design is the defect and a further patch is not the remedy. A rising complexity trend in the touched file, judged against that file's own recent baseline, is a finding the diff alone cannot show. Read the set of files in the change: a pair with no visible relationship is suspected hidden coupling, and a file that historically changes with these and is absent here is a suspected omission — the missing edit, which no compiler or test can point at. A long-stable file being edited owes more justification and more cover than a young churning one.
**Unless:** History informs where to argue and what to suspect; it never substitutes for a defect the reviewer can state. Deliberate divergence from a historical partner is a legitimate answer once given, and a coupling that keeps being overridden is dissolving rather than being violated. Never turn this into a measure of the individual author — the evidence is about code regions, and it dies the moment it is read as productivity.
**Sources:** (02, 22, 23) F2

### 11.5 Require a bug fix to run from symptom to fault, then sweep the siblings
**Finding:** A fix whose shape is a guard keyed to the reported input, a special case added at the point where the symptom surfaced, or a defensive check at a caller shows that the fault was never located. Ask where the wrong value is produced, not where it was noticed, and expect the change to land there. Then require the sweep: the same literal, the same rule, the same pattern elsewhere — every copy of duplicated knowledge is wrong the same way, and a fix landing in one of several copies leaves the defect shipped. Where a fix is deliberately containment rather than repair, that is legitimate only when it is labeled as containment, with the real fault stated.
**Unless:** Containment under incident pressure is a valid engineering choice; the finding is silence about it, not the choice. Where the fault genuinely is the caller passing garbage, the caller is where the fix belongs. A fix that must be minimal because the surrounding design cannot yet be moved is acceptable when recorded under 11.8.
**Sources:** (02, 09, 18, 22, 23) F3

### 11.6 Move a rule into the build the second time it is enforced by hand
**Finding:** A mechanical, checkable rule — formatting, import direction, layer visibility, a naming convention, a banned call, a dependency threshold — being caught by a human for the second time in this codebase. The finding is not the violation; it is the absence of the check. Ask for the check with a threshold and a named owner, so the rule survives the reviewer's attention span rather than eroding into whichever version each reviewer remembers. The same applies to compiler and analyzer output: enforce the level the project actually declares, and treat a suppression, silenced warning or ignored diagnostic added without a written reason as a finding on this diff. Raising the project's level is a separate change, not something to demand inside this one.
**Unless:** Judgment findings do not belong in the build — a check that fires on shape but cannot see intent produces noise that gets globally suppressed, taking the useful signal with it. Where tooling is structurally blind (reflection, string-built dispatch, configuration, cross-repo edges), naming that blindness is the reviewer's job and a manual convention is the only available enforcement. A first hand-catch is just a comment.
**Sources:** (08, 09, 19, 22, 23, 34) F15

### 11.7 Refuse to treat an unreadable change set as reviewed
**Finding:** A change too large or too mixed to actually be read — a restructuring carrying behavior changes, several concerns bundled, a migration whose call-site sweep buries the semantic edit, or work that arrives after weeks of hidden development. The finding is that the review cannot function as evidence, and it is stated that way rather than waved through on sunk cost: ask for the change split into pieces each of which stands alone, builds, and can be released and reverted on its own. Measure the size by the effort to reason about it, not by lines: a mechanical rename across a hundred files is readable, and forty lines of new concurrency is not.
**Unless:** Semantically atomic changes must land together — an interface with its implementation, a lockstep protocol pair, a rename with the call sites it breaks — and splitting them would ship a broken state. Never auto-reject on a numeric size threshold, and never turn this into an invitation to nitpick a change that is already readable.
**Sources:** (07, 08, 09, 10, 23) F2

### 11.8 Record the debt an approval rests on; never let it pass silently
**Finding:** An approval whose real justification is that the surrounding code is already like this, that the deadline is close, or that the right fix is out of scope. That reasoning is legitimate and must be written down in the review: what was accepted, what the correct shape would be, and what conditions the approval depends on. The absence of that sentence is the finding, because an unrecorded exception becomes the precedent the next change measures itself against, and each step looks small against what is already there. Watch specifically for new modules named for no concept — util, common, misc, shared, core — whose emptiness guarantees they collect everything, and for the argument that a pattern is fine because the codebase already does it.
**Unless:** Recording debt is not blocking on it; refusing to ship until the neighborhood is clean is its own dysfunction, and this principle asks for a recorded decision, not a refusal. Inherited mess the diff merely sits next to is not this change's to fix or to inventory — the trigger is a shortcut this change takes or extends.
**Sources:** (01, 02, 18, 22, 33) F2

### 11.9 File a cost finding from what the diff shows, and ask a question when it shows nothing
**Finding:** A reviewer may raise cost with no profile in exactly three shapes, each checkable from the diff alone. First, an operation whose cost class leaves the process, the CPU or the language runtime — a network round trip, a syscall, a disk read, a subprocess spawn, a client or connection built per call — multiplied by the real bound of the loop or the event rate it sits in, because that product, not the line count, is what the change costs. Second, a structure, scan, buffer, thread or connection whose size grows with users, rows or traffic, where a constant in review is a curve in production. Third, a serialization point introduced on a path with real parallelism — a global lock, a single-threaded stage, one shared hot structure, a widened critical section, blocking work or I/O done while holding a lock — because a serial fraction is a ceiling no hardware buys. Absent all three the objection is first-principles and stays a note that asks for the rate, never a block. State the ask as a question the author can answer and the reviewer cannot: what bounds this loop, what is this path's event rate, how many of these exist at peak — never a number the reviewer invented.
**Unless:** Off a hot path a slow operation is fine, and over-strictness on cold code is the mirror error — the cost table is triage, not a ban, and asymptotic growth ignores constants where n is genuinely bounded and small. Serialization is often necessary and cheap: the weight scales with how hot and how parallel the path is, and one global lock is right where contention is genuinely rare. The finding never buys its own remedy. An optimization offered in answer to it is an improvement claim like any other and still owes the measurement 11.2 demands, so a cache, a denormalization or a hoisted computation arriving as the fix is judged on data, not on the fact that a cost finding provoked it.
**Sources:** (31, 33) F16
