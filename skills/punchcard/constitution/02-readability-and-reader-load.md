# 2. Naming, Readability and Reader Load

This chapter answers what a reviewer does with the sentence "I could not follow this": when confusion is a reportable defect, when it blocks, and which concrete presentational causes it must be pinned to. It governs names, vocabulary, comments, local idiom and navigation cost — not decomposition remedies, which belong to chapter 1.

### 2.1 Reject any name or signature that contradicts what the body does
**Finding:** A new or changed identifier whose body disagrees with the reader's prediction: a query that mutates, a predicate-named method with side effects, a plural returning one item, a getter that performs IO or lazily writes, a name encoding an algorithm the body no longer uses, a parameter whose name states a unit or currency the code does not enforce. Also flag near-twin identifiers in one scope, where readers autocorrect one into the other. The reviewer flags the name against the specific line of the body that contradicts it, and asks for a rename or for the effect to be removed — never for a comment that warns about the lie.
**Unless:** Honest-but-imperfect names, abbreviations, case style and synonym preferences are not findings — the target is active contradiction and confusability. Short generic names in a scope small enough to see whole are fine. This principle takes no discount for team fluency, hot-versus-cold code, or diff size: a lying name is a carve-out from proportional rigor because fluent readers are precisely the ones who stop at the name.
**Sources:** (01, 09, 10, 11, 15) F14

### 2.2 Report confusion always; pin it to a cause before deciding whether it blocks
**Finding:** The reviewer could not reconstruct what the change does without opening the implementation of what it calls. This is always reported, and always pinned to the exact point where the trace broke, with a concrete presentational cause named: a name contradicting its body, an effect not visible at the call site, an abstraction-level jump inside one sequence, more chunks in play than a reader can hold (1.4 owns the counts), or a navigation hop with no discovery path. Two checks are owed before filing: grep the surrounding code for the idiom being objected to, and look for a stated non-functional constraint that shaped the odd code. If a constraint exists but is unwritten, the finding converts into a documentation finding rather than disappearing. Escalate to blocking when the construct is novel to this codebase, when the load is purely presentational, or when it sits on a security, concurrency or trust-boundary path.
**Unless:** Downgrade to a non-blocking note when the construct is an established local idiom the team reads fluently, or when the difficulty is intrinsic to the problem rather than to the presentation. "This is complicated" with no located cause and no fixable ask is not a finding — it is the noise that trains authors to stop reading reviews. State which mode the finding is in.
**Sources:** (01, 02, 08, 10, 23) F14, F2

### 2.3 Keep one concept to one name and one vocabulary across the codebase
**Finding:** The diff introduces a second name, mold or spelling for a concept the project already names, or a second way of doing what the project already does. Names the diff creates are held without negotiation to the vocabulary the domain experts actually speak in the domain layer, and to general mechanism vocabulary below it — the layer the name sits in is what makes this reviewable. For an existing name the diff renames, price the change by reach: rename outright when the build proves every consumer moved in this change; where a consumer sits outside that unit, require a deprecating delegation with a named owner and an end. A rename landing on some call sites and not others is a finding on its own — a half-migrated convention costs more than either name alone.
**Unless:** A merely better synonym for an established term loses to the existing convention; conformance beats an equally good novel name. A genuinely new concept deserves a new name, and genuinely different concepts must not be forced under one name — distinguish variants explicitly. Honesty outranks conformance: never propagate a name that lies (2.1) or that contradicts the domain experts for consistency's sake.
**Sources:** (01, 04, 10, 13, 15, 23) F12, F14

### 2.4 Treat deviation from the local idiom for a standard operation as a bug signal
**Finding:** A standard operation — iteration, comparison, null or absence handling, resource acquisition and release, error propagation, string or path building — written differently from the way the surrounding code writes it. The finding is not taste: the deviating line is where the reviewer looks for the defect, because a fragment rewritten among copied siblings is where offsets, units, epochs, bounds and encodings get silently dropped. The same applies to one half of a paired operation (open/close, encode/decode, add/remove) following a different convention from its partner, and to a new case written unlike the cases beside it.
**Unless:** An argued, stated style change is legitimate when the old idiom is itself the problem — but then it is a separate change with its own migration, not a drive-by. Real systems blend styles, and inherited inconsistency is not this diff's to fix. If the reviewer cannot name the idiom being deviated from, there is no finding.
**Sources:** (04, 10, 23) F14

### 2.5 Carry each fact in the most durable carrier available: type, then name, then comment
**Finding:** A constraint the language could have expressed is stated in prose instead — a unit, a nullability, an ordering requirement, a range — while the signature stays permissive. Ask for the type first, the name second, the comment last. Independently: a new cross-module or otherwise public surface with no interface-level statement of what the formal signature does not carry (units, ordering, inclusivity of bounds, nullability, side effects, preconditions, how failure reaches the caller) is an unfinished interface, and its absence is a real finding. In the other direction, implementation prose restating the line below it is a defect, and any comment the diff leaves contradicting the code it now sits beside is a defect of this diff, not inherited debt.
**Unless:** Rationale — why this way, what was rejected, what constraint forced it — legitimately lives in a comment or commit message and has no type to move to. Heavy type encodings can cost more than they protect; a wrapper carrying no invariant is ceremony. Do not demand ceremony on single-caller internal code, and never demand a comment on code that is already unmistakable.
**Sources:** (01, 04, 09, 11, 13, 23) F14

### 2.6 Count the navigation the diff charges the reader
**Finding:** Count the files opened and the invisible hops taken to believe the change is correct: call chains through single-use indirection, cross-file callbacks, container wiring, reflection or string-built dispatch, ambient configuration reads, and logic split across layers for symmetry. Each hop must have a discovery path a reader can follow from the code in front of them. If the fan of files keeps widening, the finding is scoping — say so as an objection to where the change was placed, not as a nitpick on any one hop. Two declarations that must agree with nothing enforcing the agreement (a parallel table, a size repeated as a literal, a doc mirroring an enum) are the same defect in its worst form: the hop is invisible and the drift is silent.
**Unless:** Genuine module boundaries and real deduplication justify indirection — the defect is undiscoverability, not modularity. Some changes are inherently cross-cutting, and a small diff is not by itself evidence of good scoping. Where the language cannot express the derivation, a stated invariant plus a check that fails on divergence closes the finding.
**Sources:** (01, 10, 13, 23) F14
