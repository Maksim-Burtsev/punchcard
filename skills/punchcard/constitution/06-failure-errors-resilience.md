# 6. Failure, Errors and Resilience

This chapter answers what happens to this diff on a bad day: how a failure is represented and typed, where it is decided, what bounds the waits and the growth it introduces, and whether anyone — a test, an operator, the next caller — can tell that a failure path works.

### 6.1 Report failure where it is detected, decide policy where the context is
**Finding:** A catch that logs and continues, an empty catch, a discarded error return, a library or lower layer that exits, prints, or picks a user-facing outcome on its own, or a handler that reacts without being positioned to decide. Also flag the mirror image: a failure re-raised in the callee's own vocabulary across an abstraction boundary, so the caller must know the mechanism below it to interpret what it got. The reviewer's question is mechanical — after this branch runs, does anyone still know the operation did not happen?
**Unless:** Top-level application code and one-shot tools may legitimately abort or print and exit. Cleanup in an intermediate frame — releasing what it acquired, leaving itself usable — is not a policy decision and is required, not flagged. Honestly refusing the request back to the caller is a decision, not a swallow. A condition that can be defined out of existence (an always-present empty selection instead of a special case) beats both a handler and a report, as long as the caller loses nothing it must act on.
**Sources:** (01, 02, 04, 14, 19)

### 6.2 Make failure crossing a boundary explicit, and type domain failures apart from technical faults
**Finding:** A value returned from an error branch that the call site cannot distinguish from success — an empty collection, a zero, a default-constructed object, a null where the happy path also returns null. A domain rule outcome (insufficient funds, quota exceeded, not found) thrown as the same generic type as an infrastructure fault, leaving message text as the only discriminator. An expected, enumerable outcome routed as an exception into an infrastructure handler. A remote or cross-process call whose code handles success and failure but not the third case, unknown. A fallback that answers quickly with something wrong instead of refusing.
**Unless:** Genuine invariant violations and bugs still throw. The ask is a small marker split, not one exception class per rule — separate types only where handlers actually diverge. Inside a module, for a locally determined condition, absorbing the case is better than representing it (6.1). A result type is only an improvement if callers are made to open it; a hand-rolled wrapper every caller unwraps with an ignored branch is not.
**Sources:** (02, 04, 14, 19, 27, 28, 30; F8)

### 6.3 Hold the diff to the codebase's one error-handling strategy
**Finding:** The change introduces a second convention for placing and propagating failure beside the one already in the touched code — per-call-site try/catch in code that propagates, a bespoke retry beside mandatory shared client machinery. Flag it and ask for either conformance or a stated migration with an owner; half-converted error conventions are worse than either one. Where the surrounding code has no articulated strategy at all, the missing strategy is the finding, not the individual patch.
**Unless:** A single diff does not relitigate exceptions versus return values. If the new convention is the project's declared direction and the diff carries the migration note, it is conformance, not divergence. A translation at a genuine boundary — an adapter recasting a vendor's errors into the local vocabulary — is the strategy working, not a second one. What is never traded away for convention is the F8 substance: a domain failure typed apart from a technical fault, a distinguishable unknown, and no error-branch value that reads as success at the call site; where the existing convention cannot express those, the convention is the finding.
**Sources:** (01, 02, 04, 14, 30; F8)

### 6.4 Bound every wait that leaves the process, and define what the caller does when it expires
**Finding:** Any call in the diff crossing a process, host, or pool boundary with no explicit timeout — sockets, HTTP, RPC, database calls, message request/reply, connection- and thread-pool checkouts, lock and queue waits — including calls through a vendor client where the socket is hidden and the default is infinite. Equally a finding: a timeout with no defined behavior on expiry, which is a rethrow into nothing or an immediate retry into the same broken dependency. For an added synchronous dependency, the reviewer asks for one named behavior while it hangs; silence is the finding.
**Unless:** In-process calls owe none of this — timeouts around a method call are ceremony. A bound picked arbitrarily is its own defect: a pool sized too small produces contention indistinguishable from a slow dependency, so a number with no basis is worth a note. Nobody owes an enumeration of every failure permutation, just one defined degraded behavior.
**Sources:** (18, 19, 28, 29, 30; F13)

### 6.5 Ship the bound with anything the change lets grow with traffic
**Finding:** A query, association traversal, or service response returning a collection with no caller-imposed limit — the callee, or the data, decides the size. A table, cache, in-memory map, session store, log or audit stream, temp file, or event row the diff adds with no shipped mechanism that removes entries. Breaking out of the loop after N rows is not a limit: the limit belongs in the request. Bounding forces the remainder question — silently truncating where completeness matters is worse than the unbounded version, so ask for pagination or streaming.
**Unless:** A result provably of cardinality one needs no limit. Retention mandated by law or by users is not sludge — move it off the production path rather than deleting it. A purge that ignores referential integrity or a domain invariant is worse than none, which is why it usually belongs in application code rather than an operator script.
**Sources:** (28, 29, 30; F13)

### 6.6 Let no retry land without an idempotency story and a bound
**Finding:** A retry loop, a poll, a redelivering consumer, or a refresh-on-failure path added over an operation whose repetition is observable — a write, a charge, an email, an order — with nothing that makes the second attempt a no-op end to end. The unknown outcome is the trigger: a timeout cannot separate a lost request from a crashed peer from a lost reply, so the caller does not know whether the work happened. Deduplication one layer down does not count. Also flag unbounded attempts, retries with no backoff, and backoff with no jitter, which turn a recovering dependency into a synchronized flood.
**Unless:** Naturally idempotent operations need no key. An honest error to the user is often the right answer and needs no retry machinery at all — handling a fault is not the same as tolerating it. Some errors must never be retried; a rejection caused by bad input is one. Where mandatory shared retry machinery exists, the finding is the bespoke local loop, not the missing one.
**Sources:** (19, 27, 28, 29; F13)

### 6.7 Design what happens when the dependency is down, and never serve a degraded answer as a fresh one
**Finding:** The diff's dependency-failure branch has no named behavior, or it silently substitutes a lesser answer — stale cache, empty list, last known value — that the caller and the user cannot tell from a real one. Prefer a fast refusal to a slow answer and no result to a wrong one: a degraded or fallback answer is a product decision, so flag one that has no owner's agreement and no distinct labelling at the point it reaches the user. Separately, flag a new consumer of a shared pool, queue, or single hot row whose misbehavior would degrade unrelated consumers of different criticality.
**Unless:** Containment machinery beyond the timeout — breakers, bulkheads, compartments — is risk-gated, not mandatory: a finding must name the failure it prevents and the path it sits on, otherwise it is a question, not a block. Breakers are decoration where a timeout suffices, and thresholds tuned to ordinary jitter manufacture outages. Partitioning trades utilization for containment; slicing finely enough to strand capacity is its own defect, and consumers that are neither independent nor differently critical need no separation. Watch for the partition that is not one — separate pools on the same database, broker, or host.
**Sources:** (14, 18, 19, 28, 29, 30; F8, F13)

### 6.8 Treat a failure path with no evidence and no outside signal as broken
**Finding:** Code the diff adds that only runs on a bad day — a fallback, degraded mode, break-glass route, restore or failover branch, a compensating action — with nothing exercising it: no test that drives the dependency to fail, no drill, no everyday traffic through the same mechanism. Prefer the emergency case implemented as the normal case with different parameters over a second implementation that rots. Alongside it, flag a new component, integration point, background job, or queue consumer that gives an operator no way to tell busy from stuck from outside the process: a health signal that stays green while the work path is blocked, a failure carrying no correlation id, or an asynchronous path that does not say where its errors go and where data can be lost.
**Unless:** A clean harness run proves survivability, not correctness — do not accept it as closing evidence, and do not demand a proof of coverage. Emergency human access to a wholly broken system may legitimately need a lower-dependency alternative that cannot reuse the normal stack, on a drilled schedule; and a test environment or scheduled drill substitutes for risky production exercise. Failure simulation never ships inside the production application. Metrics with no defined normal range are noise, collection that perturbs the hot path is a regression, and records must carry decision inputs and references rather than the payload itself.
**Sources:** (02, 04, 18, 19, 28, 29, 30)
