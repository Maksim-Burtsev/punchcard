# 29. Building Secure and Reliable Systems — Heather Adkins, Betsy Beyer, Paul Blankinship, Piotr Lewandowski, Ana Oprea, Adam Stubblefield

> Security and reliability are not features you can point at in a module — they emerge from how a system is decomposed, what each part trusts, and what it depends on, so a review must judge boundaries and dependencies rather than hunt for a security component. The two properties are built from the same machinery (isolation, recovery, observability) and constantly pull against each other: a fix for one usually creates risk in the other, and the reviewer's job is to make that trade explicit instead of letting it be decided by accident in an error branch. The book assumes the adversary is patient, the operator is tired, and the clock is wrong — so it prizes designs that can state their intended state, return to it, and prove they still can. Above all it distrusts anything that only runs on a bad day.

## Principles

### 29.1 Name the security-versus-reliability trade the change makes instead of optimizing one side silently
- **Why:** Every hardening move buys an availability risk and every availability move buys an exposure, and the loop is real: offloading sensitive data to a provider adds an outage you don't control, buffering against that outage means storing the data you refused to hold. A change justified purely as "adds security" or "improves reliability" has usually moved the other property without saying so.
- **Applies:** New services, new third-party dependencies, changes to component boundaries, and any diff whose stated rationale names only one of the two properties.
- **Unless:** This is not a licence to block feature work for speculative hardening; the book weighs initial velocity against sustained velocity and accepts that retrofitting later is sometimes the right business call.
- **Source:** Ch. 1 Commonalities; Ch. 4 Design Tradeoffs (Features Versus Emergent Properties, Payment Processing)

### 29.2 Make every failure path declare whether it fails open or fails closed, and match the choice to the asset
- **Why:** Reliability pushes code toward serving whatever it can under uncertainty and security pushes it toward denying, so leaving it implicit means an unloadable ACL or an unreachable auth backend quietly becomes allow-all — an attacker then weakens authorization with load alone. Naming the posture per path forces the author to state the minimum non-negotiable behavior.
- **Applies:** Error branches around authorization, revocation, credential verification, policy or config loading, quota — anywhere a dependency's absence changes what the system permits.
- **Unless:** Fail-closed everywhere manufactures outages; for policy distributors and mitigation controllers prefer failing static — keep serving the last known good policy — and where availability is the asset, fail open with loud alerting.
- **Source:** Ch. 8 Failing Safe Versus Failing Secure; Ch. 9 Failing Open

### 29.3 Require the system to know its intended state, and repair the intended state rather than the running instance
- **Why:** Recovery means going back to a known good state, which is impossible if nobody can say what it was; when intended state is explicit and machine-comparable, corruption, a botched rollout, and a malicious edit all surface as one detectable deviation. It also settles where a fix belongs: rebuilds, autoscaling, and restores re-materialize systems from stored images and configurations, so a patch applied only to the live instance is silently undone and the hole returns looking like a new bug — and one exploited server usually implies twenty siblings running the same flawed dependency or unsafe idiom. Wall-clock time is external state an attacker or an outage can move, and a recovery path that runs through the thing it is recovering reproduces the original failure.
- **Applies:** Host-local config, expiry timestamps and validity windows, restore and rebuild tooling, images, templates and seeds, health checks, break-glass paths, key rotation, and any vulnerability fix whose root cause is a shared library, shared idiom, or copy-pasted helper.
- **Unless:** Exhaustive state capture is expensive — rebuilding from scratch is a cruder but valid substitute at small scale, and deliberately time-bounded access is legitimate as long as a repair path exists that needs no accurate clock. Emergency stop-the-bleeding changes may legitimately hit the live system first, paired with a tracked follow-up; do not hold a time-critical fix hostage to an exhaustive audit, and the class-wide rule does not apply where the defect is provably one-off local logic.
- **Source:** Ch. 9 Know Your Intended State; Limit Your Dependencies on External Notions of Time; Ch. 18 Is Your Recovery Tooling Compromised?; Will Your Recovery Reintroduce Attack Vectors?; What Variants of the Attack Exist?

### 29.4 Distrust any code path that only runs on a bad day; make the emergency case the normal case with different parameters
- **Why:** A path exercised only during outages accumulates hidden bugs precisely because nothing routinely proves it works, and it is needed when failure is most expensive. Reusing the ordinary push, revocation, and restore mechanisms means everyday traffic continuously tests the emergency case and there is no second implementation to rot.
- **Applies:** Break-glass and override variants, fallback queues, degraded modes, rollback branches, restore and failover paths added or touched by the change.
- **Unless:** Emergency human access to a wholly broken system may genuinely need a lower-dependency alternative that cannot reuse the normal stack — the book accepts that, but demands it be drilled on a schedule. Do not require risky production exercise where a test environment or a scheduled drill will do.
- **Source:** Ch. 9 Design to Go as Quickly as Possible; Design for Testing and Continuous Validation; Ch. 5 Graceful Failure and Breakglass Mechanisms

### 29.5 Grant capability through narrow, single-purpose interfaces routed via an audited choke point — never a shell or a general host API
- **Why:** A caller handed a large surface implicitly gets everything that surface allows, so a bug in the automation or a leaked credential equals full compromise of every target. A mediated entry point that accepts three named operations adds authorization, logging, approvals, and rate limits without touching the targets — including third-party ones you cannot modify — and turns an unbounded human mistake into a rate-limited one.
- **Applies:** New admin endpoints, service accounts, deployment and config-push paths, ad hoc scripts holding production credentials, debug hooks.
- **Unless:** The proxy is a real cost and a new single point of failure needing redundancy and its own SLA; it must forward the caller's identity rather than act under its own privileged role, and it needs a break-glass route. Past a handful of distinct actions, build on an existing RPC framework instead of proliferating one-off commands.
- **Source:** Ch. 3 Case Study: Safe Proxies; Ch. 5 Small Functional APIs

### 29.6 Encode a safety invariant in a type or framework so violations cannot compile, with exactly one reviewed escape hatch
- **Why:** A raw string asserts nothing about being a safe query fragment or safe markup, so reviewing the consumer means tracing every path that could have produced the value — an obligation that grows without bound. A type whose constructors carry the guarantee shrinks review to the constructor and the sink and lets all pass-through code be ignored, which is what makes claims like "no injection in this application" affordable.
- **Applies:** Repeated hand-rolled escaping, string-concatenated queries, per-handler auth checks, retry and logging logic — especially the second or third copy.
- **Unless:** In most languages a type is not a security boundary against malicious in-process code, only against honest mistakes; it cannot catch a wrong design-level choice. A framework for one call site is speculative overhead, and one covering every corner case becomes unauditable. If the escape hatch is unreviewed or scattered, the whole scheme is theater.
- **Source:** Ch. 12 Frameworks to Enforce Security and Reliability; TrustedSqlString; Ch. 6 Understanding Complex Data Flows

### 29.7 Ask whether the change enlarges the set of code that must be correct for a security property to hold
- **Why:** Every component that can reach sensitive data or bypass a policy joins the base whose failure is a breach, and a boundary is only real if you can enumerate what enforces it. Splitting so that catalog search cannot touch customer addresses means a flaw there is no longer a data leak.
- **Applies:** New modules gaining access to a sensitive store, merged services, shared databases, frontends given broad backend privileges, parsers of untrusted input.
- **Unless:** A split is cosmetic if the protected service simply trusts its new caller — the boundary must carry per-request end-user context, not just a service identity. Outside a trust boundary, splitting code to shrink a notional TCB just adds interfaces and hurts understandability.
- **Source:** Ch. 6 DEEP DIVE: Security Boundaries; Small TCBs and Strong Security Boundaries

### 29.8 Keep failure inside an existing blast-radius boundary, and give fleet-wide operations a self-limiting check
- **Why:** A new shared dependency or cross-compartment call quietly converts a local failure into a global one, and a mistaken or partly compromised control plane can push one file that revokes every credential. When each target refuses an update that would disable itself, or the operation is sharded and rate limited, the worst case becomes a fraction of the fleet — and recovering part of an infrastructure is far cheaper than recovering all of it.
- **Applies:** Anything mutating every node, tenant, or record in one action; new global config sources; new synchronous shared dependencies; changes that let one region's or tenant's failure reach another.
- **Unless:** Compartments cost capacity and operational effort per compartment and are worthless at whole-server granularity or unmaintainable at argument-value granularity — aim at role, location, and RPC method. Self-limiting checks widen the response window rather than guaranteeing safety, and must not make legitimate large-scale rotation impossible.
- **Source:** Ch. 8 Controlling the Blast Radius, Failure Domains; Ch. 9 Revoking Credentials at Scale

### 29.9 Require bounded retries with backoff and jitter from shared client machinery, and degrade the failing feature rather than the product
- **Why:** A client retrying tightly against a struggling server turns a small failure into a self-inflicted denial of service, and an outage synchronizes clients so backoff without jitter produces coordinated bursts. Meanwhile a startup freshness check or a blanket error screen turns one timed-out backend into total loss of the product, including data already cached locally.
- **Applies:** New RPC clients, retry and poll loops, refresh-on-startup fetches, cache-miss paths, and any handler converting a backend error into a top-level failure — especially in clients you cannot update quickly.
- **Unless:** Backoff does not replace server-side throttling for clients outside your control; some errors should not be retried at all. Features no longer safe when degraded — stale authorization, unverifiable data — should be disabled and labeled, not served best-effort, and reduced guarantees must be visible to the user.
- **Source:** Ch. 10 Client Retry Behavior, Graceful Degradation; Ch. 8 Controlling Degradation

### 29.10 Base deployment trust on properties of the artifact, not the identity of whoever pushed it, and hold configuration to the code bar
- **Why:** An authenticated actor can still be mistaken or compromised, so identity checks alone leave the pipeline bypassable by anyone with the right credentials; checking the artifact's hash, origin, and build inputs survives account compromise. Configuration changes production behavior exactly as code does — a wrong backend pointer or a widened bucket ACL breaks things just as thoroughly — yet it usually escapes review entirely, and any path that skips the choke point makes the check optional.
- **Applies:** Build, packaging, and deploy changes; dependency manifests and base images; feature flags, IAM definitions, deployment manifests; anything pushing behavior to production outside the reviewed pipeline.
- **Unless:** Full pinning and verifiable-build provenance are large investments best adopted incrementally, and pinning must come with vulnerability monitoring or it hides you from patches. Some knobs cannot round-trip through review (emergency traffic draining, live capacity tuning) — require a logged, alarmed override instead of blocking. Treating config as code never means committing secrets.
- **Source:** Ch. 14 Verify Artifacts Not Just People; Deployment Choke Points; Treat Configuration as Code; Don't Check In Secrets!

### 29.11 Make sensitive actions emit granular structured records, and make every bypass loud, rare, and re-decidable
- **Why:** A log saying a session was opened tells an investigator nothing about what happened inside it, and an attacker who knows about naive session capture defeats it easily; recording the concrete operation with a content hash supports firm statements about what was and was not done. An unlogged fail-open or break-glass use is indistinguishable from an attack, and if bypasses are routine nobody can pick the malicious one out of the noise.
- **Applies:** New privileged operations, support access to customer data, emergency credentials, admission controllers and gates that disable validation, and changes to existing audit logging.
- **Unless:** Do not log the sensitive payload itself to make replay possible — record decision inputs, hashes, and structured case references rather than free text or private content. Volume nobody reviews is not an improvement, and an alarm on something that fires daily is worse than none: fix the frequency first.
- **Source:** Ch. 5 Auditing, Business Justifications; Ch. 14 Include a Deployment Breakglass; Ch. 15 Collect Appropriate and Useful Logs

### 29.12 Treat the downgrade path as a security decision: enforce a floor below which no version may run, while leaving reliability rollbacks above it
- **Why:** Both extreme policies are wrong. Permitting any rollback means the ordinary cure for a stability bug can reinstate a patched vulnerability — and the older or more public the hole, the likelier a packaged exploit already exists. Forbidding rollback outright deletes the fast route back to a known good state and makes every recovery wait on a fresh build, which is exactly the dependency incident response cannot afford. The workable middle is a floor kept outside any single release: a security version number raised once a patch has proven stable in production, and a minimum acceptable value each component ratchets upward on itself, so reliability rollbacks stay available above the floor while nothing below it will execute again. A deny list shipped inside the release cannot substitute — leave one older image reachable and an attacker steps the version backward hop by hop until they land on the vulnerable one.
- **Applies:** Deployment and release policy, self-updating components (package daemons, bootloaders, BIOS and NIC firmware), signing-key rotation, anything whose floor lives in one-time-programmable storage, and any deploy path that will accept a version older than what is already running.
- **Unless:** The full scheme — persistent component-local state, deny lists, version floors, key rotation — is a large undertaking; adopt one piece at a time, using rapid deny-listing under incident pressure and doing floor maintenance later under calm conditions. A floor burned into fuses is forward-only and can strand a device, so put the mutable logic in a small layer above it. Long-shelved spare parts need a signing key their old firmware can still verify, and a compromised release that pins the floor at maximum requires a deliberate, short-lived reset path.
- **Source:** Ch. 9 DEEP DIVE: Rollbacks Represent a Tradeoff Between Security and Reliability (Deny Lists; Minimum Acceptable Security Version Numbers; Rotating Signing Keys); Ch. 14 Provenance-Based Deployment Policies

## Review heuristics

- Find the error branch around every authorization, revocation, or policy lookup in the diff and ask what happens when the dependency is down — if the answer is "the request proceeds", that is a bypass an attacker can trigger with load.
- Grep the diff for code that runs only under failure, emergency, or overload, then ask what exercises it: no test, no drill, no everyday traffic means it does not work.
- Check whether the change hands an actor a shell, a general host API, or standing production credentials where a named operation would do — and whether the resulting action is loggable as itself.
- Ask what set of components must now be correct for the system's security claim to hold, and whether this change just added one; a "split" where the callee simply trusts the caller has added, not removed.
- For any value crossing into a query, markup, command, or redirect, check whether the guarantee travels in the type or lives in an upstream validation the reviewer would have to trace.
- Look for wall-clock time, per-host trust files, and unreviewed configuration as load-bearing correctness — and for a fix applied to a live instance rather than to the image, template, or shared helper it will be rebuilt from.
- Ask what stops a downgrade past a security fix: if the deploy system accepts any older signed version, the stability rollback everyone reaches for first is also the exploit's way back in — and check the answer is a floor, not a ban on rollback.
