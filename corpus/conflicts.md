# Conflict register

Forks where the corpus genuinely disagrees, deduplicated across clusters (the same underlying
disagreement appears once). Ordered by how much the choice changes what Punchcard flags. Book refs
are corpus numbers. Every entry ends with a decision line the skill owner fills in.

---

## F1. Build the seam now, or earn it with a second case

- **Fork:** Does an interface, port, wrapper or extension point belong in the diff that first needs the thing behind it, or only after a concrete second consumer exists?
- **Position A — Isolation and testability first (03, 06, 07, 09, 12, 17, 25):** Vendor, ORM, framework and storage types are replaceable details that must sit behind a domain-named port; hard-wired collaborator construction forecloses substitution; the arrow itself is the product, so a single implementation is fine. Cross-cutting concerns get their own decorators. Interfaces should also be somewhat general-purpose, because an API named after its one caller's business action leaks upper-layer concepts downward (01).
- **Position B — Pay rent / anti-speculation (01, 05, 13, 14, 16, 19, 21, 24, 26):** An interface with one implementation, a factory for one product, a parameter with one caller, a layer that repeats the abstraction beneath it — all are indirection nobody pays for. Extraction is cheap later; preemptive insulation over every dependency is debt bought early, and generality beyond present use prepares for the wrong change.
- **Stakes:** On a handler that calls the payment SDK directly, A files a missing-port finding and B approves; on the wrapper the author adds in response, B files speculative-indirection and A approves. Same diff, opposite comments, on a pattern that appears in most PRs.
- **Recommendation:** Synthesis on three checkable triggers, applied in the diff rather than by forecast. Require the seam when (a) the foreign type would otherwise appear in domain signatures, persisted data or a stored format, (b) the seam is what removes IO, clock, network or nondeterminism from a decision a test must exercise, or (c) the dependency already has more than one call site, or the product is broad enough to shape the architecture (ORM, broker, cloud SDK, UI framework). Also require it where the boundary is genuinely one-way — remote, published, cross-team, a wire format. Absent all of these, the wrapper is the finding. Separately, split shape from mechanism: demand shape generality now and for free (an API must not be named after the caller's business action or require caller-side pre-processing), but refuse mechanism generality (extra parameters, hooks, strategy seams, second implementations) without a caller that exists. An existing test counts as a present consumer only when it actually substitutes across the seam.
- **Decision:** Position B. Indirection must pay rent: an interface with one implementation, a factory for one product, a wrapper or layer built ahead of a concrete second consumer is the finding. Seams are earned by an existing consumer or a genuinely one-way boundary (remote, published, cross-team, wire format), never by forecast.

## F2. Zero tolerance versus proportional rigor

- **Fork:** Does every diff owe the design it would have had if planned from the start, or does demanded rigor scale with risk, churn, lifespan and reversibility?
- **Position A — Zero tolerance (01, 02, 03):** Complexity arrives as individually defensible kludges each accepted "just this once", and can never be removed one at a time; detection delay multiplies fix cost; one tolerated broken window licenses the next shortcut. After any change the design should look planned.
- **Position B — Proportional and ratcheting (08, 13, 14, 18, 19, 22):** Approve improvement over perfection and block only on concrete fixable items; effort rises and falls with risk of failure, exposure, and expected lifespan (which varies enormously); bad code costs money only where someone reads it, and change frequency follows a power law, so deep argument belongs in hotspots.
- **Stakes:** Whether a minimal patch that bolts a special case onto existing structure in a cold file blocks; whether Punchcard emits equal-weight structural findings on every PR or reserves them; whether a net improvement can be blocked for not being the ideal design.
- **Recommendation:** Split the axes. Correctness and security findings are never discounted by churn or size — a one-line config or boolean flip on a trust boundary gets the full bar. Design and maintainability findings are weighted by exposure and churn: block when the shape is expensive to undo (published or cross-team API, wire format, schema, data crossing a boundary, security or concurrency path) or when the touched code is hot or brand new; otherwise report as a non-blocking note. Keep one piece of zero tolerance unconditionally: a tactical shortcut must be *named* in the review as debt, including the sentence that approval rests on the surrounding code already being what it is. State which mode a finding is in — an unlabeled deep-design objection on cold code is the noise that trains authors to ignore the reviewer.
- **Decision:** Position B. Demanded rigor scales with risk of failure, exposure, expected lifespan and churn; approve improvement over perfection; every blocking comment ties to a concrete fixable item; deep design argument is reserved for hotspots and expensive-to-undo shapes.

## F3. What makes duplication a finding

- **Fork:** Is the trigger the number of copies, evidence that the copies change together, or the boundary they span?
- **Position A — Rule of Three / one version (01, 02, 03, 05, 08, 24):** Knowledge in two places is a defect on sight; tolerate a second copy, block the third; forks and vendored copies partition the codebase and security fixes must chase every one.
- **Position B — Change axis and history (07, 11, 22):** Deduplicate only what changes together for the same actor; an abstraction pulled from lookalikes inherits conflicting reasons to change and degenerates into flags; prefer moving related code next to each other over extracting a helper without co-change evidence.
- **Position C — Boundary economics (07, 17, 19, 20, 21):** Across a deployment, repo or team boundary, a shared component trades duplication cost for lockstep-upgrade coupling; reuse is licensed by low volatility, not by neat abstraction, so duplicating a small representation is often the cheaper trade.
- **Stakes:** A third copy of a validation rule: A blocks the diff, B asks for co-change evidence first. A proposed shared package spanning two services: A approves, C flags it as manufactured coupling. Both directions produce findings on the *other* school's fix.
- **Recommendation:** Make the count a trigger and the change reason the verdict. Duplicated *knowledge* — a format, rule, invariant, protocol, magic value where one side changing makes the other silently wrong — is a finding on sight inside one deployment and ownership boundary, no history required, because the coupling is provable from the diff. Code that merely looks alike needs co-change evidence, or history-free fallback to Rule of Three in new files; the default remedy where unification is unclear is proximity plus a named note, not a premature helper. Across a deployment or ownership boundary, duplication wins unless the shared piece is both genuinely abstract and slow-changing with an owner. Fixed exceptions that stay single-sourced at any distance: protocol and wire handling, serialization formats, security primitives, and cross-cutting operational concerns.
- **Decision:** Position A. Knowledge living in two places is a defect on sight: tolerate a second copy at most knowingly and briefly, block the third; forks and vendored copies are findings because every fix must chase every copy.

## F4. Domain types versus data-shaped code

- **Fork:** Does every domain-meaning value, rule and entity belong in a constrained type with always-valid construction, or does the store and platform legitimately shape the code?
- **Position A — Type-driven domain modeling (05, 09, 11, 13, 15, 17, 25, 30):** A primitive carrying domain meaning re-delegates its rule to every caller and one forgetful caller is enough; objects must be valid the instant they exist; rules in services cannot be verified by experts; the database and framework are replaceable details that must not name themselves in domain code.
- **Position B — Pattern-fit and tooling reality (02, 04, 14, 16, 24, 27):** Domain-logic style is a choice among transaction script, table module and domain model driven by rule complexity and by the record-set structure the platform's tooling speaks; CRUD-ish logic does not repay a rich model or mapping ceremony; ORMs need field-level hydration; a distinction the application never behaves differently on earns no type.
- **Stakes:** Whether "primitive obsession" and "anemic model" fire as standing findings on half of all enterprise diffs; whether an ORM-required no-arg constructor is a defect; whether entities mirroring tables get a boundary-leak finding.
- **Recommendation:** Take B as the default posture and keep A where it earns its keep, using triggers visible in the diff. Flag a primitive when a rule about it is already checked somewhere the type could hold it, when two same-typed neighbours in one signature can be silently swapped, when it needs a qualifier that currently travels separately (currency, unit, tenant), when it recurs across many signatures, or when it reaches a sink or decision (query, markup, command, path, redirect, authorization) — otherwise say out loud that no wrapper is wanted, since a wrapper with no invariant is ceremony both schools reject. Anemic-model style is answered by the repository, not the PR: a rule landing in a service is an inconsistency finding only where a domain model already exists; it escalates regardless when the same rule now appears in a second handler or lands where the code has been patched before. Accept a non-public no-arg constructor mapped by field for persistence, and flag only when domain callers can reach those setters, when state can be written without a named transition, or when hydration can build what the constructor would reject. Flag storage or framework types above the adapter only when object and schema must evolve independently, or when the type crosses a published, remote or cross-team boundary.
- **Decision:** Position B. Domain-logic style follows rule complexity and platform tooling: CRUD-ish logic does not owe a rich model or mapping ceremony; ORM-shaped constructors and table-mirroring entities are legitimate; a distinction the application never behaves differently on earns no type.

## F5. Unit size and decomposition

- **Fork:** Is a long or growing function a finding, is the extraction the finding, and does a numeric threshold decide?
- **Position A — Extract until one thing (06, 11):** A function does one thing at one level; a large function is a missing class; blocking the diff that makes the biggest unit bigger is what stops rot.
- **Position B — Smaller is not better (01, 02, 13):** Subdivision costs interfaces, glue and distance; data does not show 100–200 line routines to be more error-prone, while nesting past three levels and about ten decision points is; a dust of tiny methods scatters the idea as badly as one lump.
- **Position C — Budget and trend (09, 22, 08, 10):** Measure comprehension load — branches, live variables, dependencies, roughly seven chunks — and judge against the file's own baseline; but do not turn a judgment call into a numeric auto-reject.
- **Stakes:** Thirty lines appended to a 600-line method: block pending decomposition, approve because the interface stayed simple, or note the trend. And whether the follow-up diff that extracts five helpers gets flagged in the opposite direction.
- **Recommendation:** Never file a finding whose stated reason is length, in either direction. Use the numeric budgets as a trigger that opens an investigation, never as an auto-reject: hard budget applies to units the diff *creates*; trend against baseline applies to units it merely extends. The blocking signals are branch count, nesting depth, and live variables plus dependencies in play together past roughly seven, and mixed abstraction levels inside one sequence (a raw SQL, SDK or bit-twiddling statement among intention-named calls). When it fires, ask for the smallest remedy in scope — new behavior sprouted as a separately tested unit rather than a drive-by decomposition of the host. File the reverse finding too: an extraction whose pieces cannot stand alone, or that breaks a loop's early exit, is a defect against the refactoring.
- **Decision:** Position B. Length alone is never a finding, in either direction; subdivision costs interfaces and glue; the signals that matter are nesting past about three levels and decision counts around ten, not line counts, and a dust of tiny methods is as much a defect as one lump.

## F6. Test doubles and test levels

- **Fork:** What is a test allowed to fake, and at what level does a feature's evidence live?
- **Position A — Mockist / outside-in (25):** Objects are defined by the messages they send, so expectations on collaborators are the primary design feedback; every feature starts from a failing acceptance test in domain vocabulary driving the real system.
- **Position B — Classicist / cost-bounded (08, 26):** Mock only dependencies other systems can observe, at the outermost adapter; everything in-process runs for real and is judged by final state. Wide tests clear a much higher value bar — one longest happy path per scenario, edge cases in fast in-memory tests. Expected values are literals from an independent source, never expressions that re-run the production rule. Tests are code and code is liability.
- **Position C — Middle (02, 24, 09):** Mocks are one isolation tool but every assertion states an exact result and fakes can drift; keep a suspicious duplicate whenever deleting it costs confidence; boundary triples and bad-data classes are where defects actually cluster.
- **Stakes:** Whether five expectations on in-process collaborators are the design conversation or overspecification; whether a feature with only unit tests is missing evidence; whether a batch of near-identical boundary tests is diligence or padding; whether a deletion of thirty tests is welcome.
- **Recommendation:** Classicist default: a double is justified only where the dependency is out-of-process and its call pattern is observable outside the system, or where the real thing is slow, nondeterministic or side-effecting. Keep the mockist reading of the evidence though — a wall of expectations or a chain of stubs is reported as a production-design finding, not merely deleted. Test level: one outside-in test per user-visible feature through the real entry point, every variation and error case below it in fast in-memory tests; file both symmetric findings (no outside-in evidence, and slow tests duplicating in-memory cases). Expected values are literals; any expected value computed from the inputs by the same rule as the code under test is a finding. Demand a boundary case wherever the diff introduces a comparison, loop bound or index, one representative per equivalence class elsewhere. Pruning is allowed with the burden on the deleter — show which other test fails if this one goes — and any deletion or weakened assertion sharing a diff with a production change is an automatic block.
- **Decision:** Adopted as recommended.

## F7. Trust boundaries and untrusted input

- **Fork:** Validate once at the region's edge and trust the type, or stack unlike controls and assume the caller is wrong — and how tolerant should a consumer be of data it does not understand?
- **Position A — Trust regions (09, 14, 30 inner):** Validate once at the edge, parse into a type, then delete the downstream guards; repeated interior checks drift apart into inconsistent rules an attacker probes, usually cope by doing nothing, and mean the code does not trust its own design. Co-designed neighbours may trust each other under an explicit contract.
- **Position B — Layered defense and assume breach (02, 18, 27, 29, 30 outer):** No single mechanism may be the defense; a config setting is invisible in review and disappears on a library upgrade. The caller's identity guarantees nothing — a compromised or paused actor can be wrong — so enforcement belongs at the resource with per-request context.
- **Position C — Tolerance (21, 27):** Bind only to fields actually consumed and accept liberally, because producers and consumers are never upgraded at the same instant; a consumer that decodes to its own model and re-encodes silently deletes fields it did not understand.
- **Stakes:** Whether a second check behind an already-validated boundary is duplication or a needed layer; whether an internal RPC accepting an already-authorized userId is inside the trust region or a bypass; whether defaulting a missing field is resilience or silent corruption.
- **Recommendation:** Count kinds of control, not checks. If the second check passes and fails on exactly the same inputs as the first, it is duplication — flag it and ask for the parsed type. If it is a different kind of control at a different boundary (parse at the edge, a uniqueness constraint at the store, a rate or blast-radius cap), it is layering and is endorsed where failure is costly. "It was already validated" is an argument only when the reviewer can point at the enforcing site; if the barricade is not locatable, the missing boundary is the finding. Draw trust regions by attacker reachability and blast radius, never by team ownership: inside one process and deploy unit, contract-only trust is right; across a process, network or privilege boundary the check sits at the resource with per-request end-user context. On tolerance, split per field: tolerate everything the code does not read (unknown fields, unbranched enum arms, extra payload), fail loudly at the boundary before any state change on anything consumed and uninterpretable. Read-modify-write through a local model over a shape another writer also produces is a finding — restrict the write to owned fields or round-trip the remainder. Two independent findings on records: a privileged action with no audit trail, and unbounded personal content inside one.
- **Decision:** Adopted as recommended.

## F8. How failure is represented and what happens when a dependency is down

- **Fork:** Absorb the condition or make failure explicit; and does an unavailable dependency fail closed, fail static, or degrade?
- **Position A — Absorb / define the exception away (01):** Handlers are the expensive part of errors — they multiply across callers and are rarely exercised — so redefine semantics until the condition is not exceptional; every new error type and per-site catch is a cost to challenge.
- **Position B — Explicit failure and fail fast (02, 04, 14, 27, 28, 30):** Failure crossing a boundary is represented explicitly, with three outcomes including unknown and domain failures typed apart from technical ones; prefer a fast refusal to a slow answer and no result to a wrong one; expected outcomes belong in return values, not exceptions routed into infrastructure handlers.
- **Position C — Degrade (29):** Fail-closed everywhere manufactures outages: fail static on last known good policy, degrade the failing feature rather than the product, and never turn one timed-out backend into a blanket error screen.
- **Stakes:** Whether a newly introduced error type is avoidable complexity or required honesty; whether an empty-list fallback is a silent wrong answer; whether a propagated 500 is an avoidable outage; whether introducing a Result type into an exception codebase is a fix or a second convention.
- **Recommendation:** Split by boundary. Inside a module, for locally determined conditions, absorbing wins — an always-present empty selection beats a special case. At any process, trust or integration boundary, and anywhere data, money or an acknowledged write can be lost, explicit failure wins. The concrete finding that separates them: a value returned from an error branch that is indistinguishable at the call site from success. On mechanism, consistency is the tiebreak — a single diff does not relitigate exceptions versus returns — but flag conflation independently: domain rule violations must be distinguishable by type from technical faults, or message text is the only discriminator left. On posture, the finding is an *undeclared* one: every dependency failure branch states whether it fails open, closed or static. Hard rules on top — authorization, revocation, quota and integrity paths fail closed; a failure may never grant a capability the principal did not already hold; policy distributors may fail static only on a complete last-known-good artifact with bounded age and an alert on use; a degraded read is acceptable only when labeled distinctly from fresh and agreed by an owner.
- **Decision:** Position B. Failure crossing a boundary is represented explicitly: domain failures typed apart from technical faults, three outcomes including unknown; prefer a fast refusal to a slow answer and no result to a wrong one; expected outcomes live in return values, not exceptions routed to infrastructure handlers.

## F9. Distribution and where boundaries go

- **Fork:** Is a process boundary a last resort, a granularity dial, or the right answer to ownership and security exposure — and what is the remedy when one feature ripples across services?
- **Position A — Don't distribute (16, 18):** Inter-process calls are orders of magnitude slower and remoteness forces coarse awkward interfaces that damage the design permanently; the burden of proof falls on any deviation from the presumptive architecture.
- **Position B — Granularity as trade-off (19, 20):** Splits are legitimate on a named driver — fault isolation, differing scale, volatile code, restricted access — weighed against the integrators; coarse is not automatically safer. Ownership and communication structure legitimately place seams (21, 22). Splitting so one service cannot reach sensitive data shrinks what must be correct (29).
- **Position C — Boundaries run through services (17):** A split is not decoupling by itself; real boundaries are internal components obeying the dependency rule, so a cross-cutting feature arrives as a new component rather than a coordinated edit everywhere.
- **Stakes:** Whether extracting a service for a second team, or around sensitive data, is approved or flagged as an expensive one-way door; and whether a four-service changelist earns "add a component in each" or "these boundaries are wrong, consider merging".
- **Recommendation:** Keep the burden of proof on the new process boundary, expressed in the granularity vocabulary. The finding fires when no driver is named, when both halves share deploy, test and scale profile, when a local join becomes a remote fetch on a hot path, or when the split leaves a shared store, schema, entity library, release train or cross-cutting feature behind — that buys coordination cost and network failure modes while buying no independence. Ownership legitimately decides *where* a boundary goes, not whether it becomes a process boundary. A security split is endorsed only when the reviewer can name both the asset that becomes unreachable and the per-request end-user context the callee enforces; otherwise ask for in-process isolation (type-enforced access, one door, separate credentials). Where a split does earn independence, require the coarse facade holding no logic plus the remote checklist: timeout, failure path, unread payload fields, authentication, idempotency. For cross-service ripple, name the boundary as misplaced and put merge-or-move-ownership on the table, using co-change history where available; reserve the internal-component remedy for services that are genuinely separate quanta where the cross-cutting thing is a variation point. Reads against tables the reading component does not own are a finding regardless of volume.
- **Decision:** Adopted as recommended.

## F10. Who enforces the invariant, and how wide is one transaction

- **Fork:** Does a business rule live in the domain model, in the store, or in a coordinator — and may one unit of work span aggregates or services?
- **Position A — Domain model (05, 15, 30):** The rule belongs to a named type or aggregate root whose construction cannot build an invalid value and whose root is the only door; one aggregate per transaction, cross-aggregate rules eventually consistent.
- **Position B — Store and resource (16, 27):** Any invariant two concurrent transactions can break must be enforced by the store: a unique constraint, an atomic operation, a compare-and-set on a version. Check-then-write in application code is write skew that survives review, tests and snapshot isolation and appears only under load; a lease holder can be paused past expiry, so only the resource can refuse a stale writer.
- **Position C — Coordinator and eventual consistency (16, 19, 20):** One business transaction gets one unit of work committing together; and where writes do span services, prefer eventual consistency with retry and compensation, because a cross-service transaction is usually the boundaries telling you they are wrong.
- **Stakes:** Whether a check-then-save inside a well-named aggregate is approved or flagged as a lost-update defect; whether a single local transaction touching two aggregates is a defect or the cheapest correctness available; whether a cross-service compensation is sufficient.
- **Recommendation:** The store is the authority under concurrency, the model is where the rule is named. A check-then-write in application code is a finding unless the row is private to the request or a constraint, atomic operation or version check makes the second concurrent write fail — one mechanical question the reviewer answers from the diff: what makes the second concurrent request fail? A constraint with no corresponding domain concept is a finding only where a domain layer exists. Transaction span: inside one store, a local transaction crossing aggregates is not a defect, and splitting it into eventual consistency needs a named driver; the findings run the other way — eventual consistency introduced with no reconciliation and human escalation path, and an aggregate boundary cited to justify a write that now crosses two stores. Classify the invariant before judging topology: permanently-wrong or preceding an irreversible action means it needs a single owner and the split is probably misplaced; compensable by an existing business process means eventual consistency is fine and the finding narrows to the missing retry and escalation. Locks: a lock row in the same store as the write, checked inside the committing transaction, is its own fence; a lock held elsewhere protecting a write the target store accepts from anyone needs a version or token the write is conditional on. Business state ("what is forbidden now") belongs on the entity; process state (attempts, step reached, compensation pending) needs a named owner and its own storage — one field serving both is the finding.
- **Decision:** Adopted as recommended.

## F11. The legacy exception

- **Fork:** May a diff into untested legacy code do things that would be blocked in new code — widen visibility, restructure without tests, pin a known-wrong behavior, rely on coarse end-to-end coverage?
- **Position A — Legacy rescue (06, 22, 24):** Dependencies often must be broken before any test can exist; the catalog deliberately makes design worse first, and a reviewer who blocks every ugly seam blocks the only exit from untested code. Actual behavior outranks intended behavior, so characterization tests record what the code does. Black-box and pinch-point tests are what make the first split safe.
- **Position B — No exception (05, 07, 08, 09, 26):** Never accept test-only backdoors or widened visibility whose only new caller is a test — the missing seam is a design defect. A refactoring without before-and-after green tests is an unverified rewrite. Application-level tests localize errors poorly and run too rarely to be the evidence for localized logic. A test that canonizes a defect is inertia.
- **Stakes:** Whether a private-to-protected change, a no-tests extraction, a characterization test asserting a wrong rounding, or a single end-to-end test as the whole safety net gets blocked or approved.
- **Recommendation:** The exception is real but narrow and conditional on facts the reviewer can check: is the touched code pre-existing and untested, and is this diff actively bringing it under test? If yes, accept declared in-source seams (widened visibility, extracted interface, injected collaborator) as booked debt with a named follow-up, accept mechanical signature-preserving dependency-breaking without tests provided the characterization test lands in this or the next PR, and accept coarse black-box or pinch-point coverage as the safety net for a behavior-preserving step. If no — new code, or code already under test — the answer is the missing class, and no-tests-no-restructuring holds. Unconditional blocks inside the exception: reflection or covert access into privates; "while I was in there" logic changes riding the mechanical move; a coarse safety net with no expiry, owner or replacement named; and a fast local test is still required for any behavior change, including behavior sprouted alongside a rescue. On characterization tests, silence is the finding in both directions — a quirk pinned with no callout, and worse, a quirk silently corrected inside a behavior-preserving diff.
- **Decision:** Adopted as recommended.

## F12. Breaking a shared contract: reshape now, or expand and contract

- **Fork:** When a diff changes a shared signature, payload, column or name, does the owner migrate everything atomically, or stage it so dependents move on their own schedule?
- **Position A — Reshape in one step (05, 13, 24):** Public is not published; when every caller is reachable, rename and reshape in one commit — demanding compatibility shims for in-repo APIs freezes structure prematurely and is itself the anti-pattern.
- **Position B — Owner internalizes the churn (08):** Every observable behavior of widely used code is a de facto contract, so a deprecation needs a named replacement, mechanical prevention of new uses and a removal plan; policies that make every caller adapt do not scale.
- **Position C — Expand then contract (04, 21, 27):** Break in two phases so each dependent migrates independently, never a flag day; give old behavior a new name rather than silently changing what an existing one does; and prefer reversible steps — append over overwrite, new representation beside the old.
- **Stakes:** Whether a PR changing a signature and its forty call sites in one commit is exactly right or missing a shim and a deprecation; whether a domain-vocabulary rename of a widely referenced type is demanded, staged, or left alone; whether a rollback path is prudence or a way to reinstate a patched hole.
- **Recommendation:** Gate on the atomicity of the consumer set, not on the word "public": if the build can prove every consumer moved in this change, the one-shot reshape is correct and a compatibility shim is the finding. The moment one consumer sits outside that unit — another repo, another deploy cadence, persisted data, a wire format, a published package, or any behavior other code could have latched onto — require expand-then-contract with a named owner and an end date, and treat an unversioned in-place break as the finding. Both schools already agree on the thing worth blocking: two live paths with nobody named to delete one. On naming, the diff's own new names are non-negotiably held to the domain vocabulary; existing names scale with reach — rename now when all callers are in-repo, otherwise rename with deprecating delegation and a migration note, never silently and never with a shrug. Half-migrated conventions are worse than either name. On reversibility, keep rollback as the default and flag a blanket no-rollback policy, but where the change is itself a security fix or a promised deletion, ask what prevents landing below it — a version floor, append-over-overwrite.
- **Decision:** Adopted as recommended.

## F13. How much resilience machinery a remote call owes, and where it lives

- **Fork:** Does every integration point get the full stability toolkit by default, or is machinery beyond a timeout gated on measured risk — and does it belong in shared infrastructure or at the call site?
- **Position A — Stability patterns (28, 29):** Every cross-process wait bounded, every result set limited by the caller, every accumulator shipped with its purge, circuit breakers on failure-prone dependencies, bulkheads on shared pools — justified because run cost dwarfs build cost. Put retries, timeouts and auth into shared client machinery so review shrinks to the constructor.
- **Position B — Cost of mechanism (01, 14, 16, 18, 19, 27, 30):** Each mechanism is new state and a new failure mode: breakers are decoration where a timeout suffices, thresholds tuned to ordinary jitter manufacture outages, retries on non-idempotent operations are harmful, and a policy abstraction over one call site is the pass-through layer that adds surface and contributes nothing. Rigor stops when the risk subsides.
- **Stakes:** A plain HTTP client on a request path: blocked for a missing breaker and bulkhead, or approved with the breaker itself flagged as unmeasured complexity. And whether a hand-rolled retry loop or a new resilient-client wrapper is the finding.
- **Recommendation:** Tier it, because an undifferentiated five-pattern checklist gets ignored wholesale and takes the timeout down with it. Tier 1, unconditional on any out-of-process call, no measurement required: an explicit timeout including pool checkouts and vendor-hidden sockets, a defined caller behavior on expiry, a caller-imposed result limit, and a purge for anything traffic-driven the change accumulates. Tier 2, conditional on a stated idempotency story: bounded retries with backoff, jitter and a client-originated idempotency key. Tier 3, risk-gated on a named scenario (request-handling path, a neighbouring consumer to protect, observed failure history): breakers, bulkheads, compartments, fault-injection harnesses — the finding must name the failure it prevents. Missing Tier 1 is a defect; missing Tier 2 is a defect only where a retry already exists; missing Tier 3 is a question, not a block. On placement: first copy inline is fine, the second copy is the finding, and a shared mechanism that callers can bypass is a finding regardless of copy count — where mandatory machinery exists, a bespoke local retry loop is the defect. When an author objects on cost, require the recurring figure that not having it buys, compared against the one-time build.
- **Decision:** Adopted as recommended.

## F14. When readability is a finding

- **Fork:** Does reviewer confusion block; are comments an admitted failure or the larger half of an interface; and does a better name lose to the codebase's existing one?
- **Position A — Obviousness is the reader's (01, 02, 11):** A first reader's confusion is itself the finding and predicts future bugs; the author fixes the code rather than arguing the reviewer into understanding. Every comment is a claimed failure to express intent in code, and comments drift into lies.
- **Position B — Charge only extraneous load (08, 10, 23):** Extraneous load is relative to actual readers — a construct the team reads fluently is not a defect because one reviewer dislikes it; look for the non-functional constraint that shaped odd code, and review against the architecture the code already follows; every blocking comment must name something concrete and fixable.
- **Position C — Contract documentation and types (01, 09, 13, 15):** The informal half of an interface — units, ordering, nullability, side effects, preconditions — is usually larger than the formal part, and without it the abstraction does not exist; but encode it in a type where the language can, since types never go stale. And code names must match the domain experts' vocabulary even where the codebase says otherwise.
- **Stakes:** Whether "I could not follow this" blocks, comments, or is dropped; whether a new public method's doc comment is asked to be deleted, required, or converted into a type; whether a better synonym for an established term is welcomed or flagged as a second vocabulary.
- **Recommendation:** Report confusion always, block conditionally, and always pin the finding to the exact point where the trace broke, naming a concrete presentational cause — a name contradicting its body, a hidden effect, an abstraction-level jump, a chunk count, a navigation hop with no discovery path. Two cheap checks are owed first: name the surrounding idiom (grep before objecting), and look for a stated non-functional constraint. Escalate to blocking when the construct is novel to this codebase, when the load is purely presentational, or when it sits on a risk or trust-boundary path; downgrade to a note when it is an established local idiom or the difficulty is intrinsic. When a constraint explains the oddity the finding converts into a documentation finding rather than vanishing. Carve-outs that ignore team fluency entirely: lying names and hidden side effects. On comments, order the demand — type first, then a required interface-level contract comment on any new cross-module surface (its absence is a real finding), and treat implementation prose that restates the line below it, or any comment the diff left contradicting its code, as defects. On vocabulary, honesty first then migration cost: never propagate a name that lies or contradicts the domain experts; a merely better synonym loses to the existing convention, and introducing a second vocabulary is the finding. Business vocabulary is required in the domain layer, general mechanism vocabulary below it — the layer test is what makes it reviewable.
- **Decision:** Adopted as recommended.

## F15. What closes a claim

- **Fork:** Is a passing CI test sufficient evidence, or do some claims require a structural constraint or a measurement — and when is missing rationale itself a finding?
- **Position A — Automated tests are the currency (08):** Only CI-visible tests count; untested behavior is unprotected and fair game to break; bespoke rigs outside CI do not count.
- **Position B — Find versus prove (02, 09, 18, 27):** Any number of passing tests can miss a locking bug or an invariant violation, because universal claims must hold in every execution; unit testing catches a minority of defects; risky quantitative claims need a measurement on the running system, not a model.
- **Position C — Concrete items only (08, 19):** Vague disapproval corrodes trust, every blocking comment ties to something fixable, and not every commit needs a decision record — design choices inside a module belong to the author.
- **Stakes:** Whether a concurrency, authorization or protocol change with a green test is approved as proven; whether "what else did you consider?" is a finding; whether a new boundary with no stated rationale blocks.
- **Recommendation:** Classify the claim before pricing the evidence. Existential claims — this input yields this output, this bug no longer reproduces — are closed by a CI-visible test, and its absence is a blocking finding naming the specific missing test. Universal claims — never deadlocks, always authorized, this invariant holds, this protocol conforms — take the test as necessary but never closing: demand locatable enforcement (a type that makes the illegal state unrepresentable, a constraint, a single-writer rule, a supervisor, a static check). Performance and capacity claims need a measurement on the running system. Independently, sabotage every green suite: would a hard-coded or degenerate implementation still pass? On rationale, scope by reach: block only when the change establishes a rule other code must follow (a new boundary, a communication style, a data-ownership shift, a lock-in dependency) or rides on an unfalsifiable quality claim, and make the ask concrete — the cost and who pays it, or the claim restated as stimulus, response and measure. Elsewhere it is a comment. Enforce the project's declared warning level rather than an ideal one; a silencing edit without a written reason is a finding, and raising the level is a separate change. When the same structural rule is enforced by hand a second time, the recommendation becomes a build check rather than a third comment.
- **Decision:** Adopted as recommended.
